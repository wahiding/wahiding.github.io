Section 02 — QA Engineer

Every system is a claim. My job is to test the claim.

I work backend and API testing on Ding's payments platform — tracing a failure from a Jenkins log back to the line that broke it, then documenting it so no one has to trace it twice.

Currently QA Engineer, Platform & Partners team, Ding. Backend and API testing, CI/CD pipelines, automation triage.

A defect rarely announces itself. It hides in a currency format, a feature flag left half-toggled, a race condition that only shows up under load. My work is the process of narrowing that down — schema, required fields, business rules, edge cases — until the root cause is undeniable, not just plausible.

The most useful bug report isn't the one that says "it's broken." It's the one with the correlation ID, the environment, the exact steps, and a clear line between symptom and cause. Writing has always been part of testing, for me — the report is what makes the fix possible.

Lately that's meant building tools rather than just running them: automation that classifies failed test runs by likely root cause, workflows that pull ticket context and cross-check it against a pull request before a human ever has to open both tabs.

Focus Areas

Backend & API Testing

Schema validation, business rules, integration edge cases.

Root-Cause Analysis

Correlation-ID tracing across services before a bug gets raised.

QA Tooling

Automation-assisted failure triage, acceptance-criteria review workflows.
